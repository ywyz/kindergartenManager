# KindergartenManager 产品经理指南

> **文档性质**：面向产品经理的范围评审、需求拆解与验收规划指南，不是用户操作手册，也不是生产可用性声明。
>
> **适用版本/基线**：以当前 `main` 与 `v3.4.0-beta2` 发布事实为基线；后续工作树、发布环境和目标平台仍需按实时代码、路线图与验收证据核对。
>
> **更新时间**：2026-08-31。
> **状态提醒**：本文中的“已实现”表示当前代码或已接受的契约存在；不等于所有平台、Word、MySQL、真实 AI、浏览器或生产环境门禁都已完成。路线图状态以 [`docs/ROADMAP.md`](ROADMAP.md) 和对应验收证据为准。

## 1. 先用一句话理解产品

KindergartenManager 是面向幼儿园教学工作的模块化单体应用：教师在一个受保护的 Web/桌面界面中完成每日活动计划、游戏观察、一对一倾听、自制教玩具和课程审议，并将 AI 作为可编辑的辅助工具、将结果保存为可追溯的业务记录和固定 Word 文档。

它解决的主要问题是“教学记录与计划分散、重复编写、难以复用和难以导出”。产品价值不是让模型替教师做最终判断，而是让教师更快形成、核对、修改和留存教学材料；幼儿姓名、观察文本、图片、教师信息、密钥和导出文件都属于需要控制的数据。

当前形态是一个 Python/NiceGUI 模块化单体，默认可使用本地 SQLite，也可配置 MySQL；AI、节假日、图片存储和 Word 导出通过明确的集成边界接入。`services/` 目前只是未来拆分的规划目录，并不是已经运行的微服务集合。

### 用户与角色

当前代码保留三类角色：

- `teacher`：以自己的当前会话使用教学记录与计划功能。
- `teaching_admin`：教学管理角色；具体可见范围应以当前权限测试和产品规则进一步确认。
- `sys_admin`：系统管理员，可访问账号管理入口并处理用户生命周期。

所有角色均通过本地账号登录。产品评审时应把“使用者”和“数据归属者”同时写清楚：UI 业务数据按可信会话的 `tenant + user` 读取，不能只凭记录 ID 判断可见性；外部 API 是另一个服务主体，见第 4 节。

## 2. 典型业务闭环与用户旅程

### 2.1 首次使用闭环

1. 管理员在应用主机上通过受控的 bootstrap 命令初始化或恢复账号；空库不会自动创建固定管理员，也不挂载匿名注册。
2. 用户访问 `/login`，登录后进入 `/home`；`/` 会跳转到登录页，业务页面需要有效会话。
3. 在 `/settings` 配置学期起止日期、年级、班级、教师、室内区域与户外内容；按需要分别配置文本模型和视觉模型。
4. 在 `/prompts` 按任务类型创建、切换或回滚提示词版本。
5. 先用手工编辑能力完成业务，再逐项启用 AI；AI 未配置或不可用时，不能把主流程设计成完全不可用。

### 2.2 每日活动计划闭环

```text
选择日期/核对周次和节假日
        ↓
粘贴教案或手工输入
        ↓
AI 拆分、年龄适配、活动生成（可选）
        ↓
教师逐项核对和编辑
        ↓
保存到当前计划 → 历史查询 → 单条或批量导出 Word
        ↓
（可选）受控 Agent 生成字段级 Patch → 教师显式确认 → 本地应用层写入
```

产品验收要点是“AI 结果可编辑、原文与适配稿可追溯、保存不覆盖并发更新、导出内容可核对”。每日计划保存和删除都携带页面实际读取的计划 ID 与 `revision`；页面过期时应提示重新加载，而不是静默覆盖或误删另一版本。

### 2.3 观察与教研闭环

- **游戏观察**：选择日期、环境和区域，上传 1–3 张图片，视觉 AI 生成观察目标、记录、评价和支持策略；教师编辑后保存、查看历史或导出 Word。
- **一对一倾听**：围绕健康、语言、社会、艺术、科学五个领域填写日期与工作日，按领域上传图片或一次导入至少 15 张，生成并编辑指标、评价和支持策略，再保存、覆盖、删除或按不同方式导出。
- **自制教玩具**：输入需求，生成名称、材料和玩法，人工编辑后保存并导出。
- **课程审议**：输入活动元数据和原始教案，生成拆分内容与审议调整，编辑二次修改稿后保存、查看历史、删除或导出。

这四类流程共同遵循“生成不是事实，教师编辑后的内容才是业务事实”。需求拆解时，应分别定义每个模块的输入、AI 可选性、保存时机、历史/删除语义、图片处理和 Word 结果，不能用每日计划的验收结论替代其他模块。

## 4. 当前能力、不支持项与身份边界

### 4.1 NiceGUI UI：本地可信会话边界

- 业务页面要求当前有效的本地 JWT 会话；会话包含唯一 `jti`，并以数据库中的 active 用户、角色、显示名和 `auth_epoch` 为权威。
- 每个敏感页面 callback 在执行保存、AI、文件、导出或删除副作用前重验页面打开时的会话；退出、重新登录、过期、停用、降权或改密后，旧标签页不能继续使用旧 actor。
- UI 资源按 `tenant_id + user_id` 投影读取和写入。记录 ID、日期或隐藏字段不是授权依据。
- PyInstaller 冻结模式只监听 `127.0.0.1`；源码/Docker 可能监听外部地址，必须另行配置 TLS、强密码和网络访问控制。
- 旧版“固定单用户 UI”是 [`ADR-0002`](ADR/ADR-0002-single-user-ui-and-tenant-api.md) 的历史产品边界；当前工作树的可信 UI 会话由 [`ADR-0006`](ADR/ADR-0006-trusted-ui-session-and-confirmed-agent-write.md) 收敛。ADR-0002 中“API 与 UI 是不同主体”的原则仍然有效。

### 4.2 `/api/v1`：独立的 tenant 服务边界

- `/api/v1/health` 免鉴权，只表示 HTTP/进程存活，不能证明数据库 readiness、UI 登录或全链路业务可用。
- 业务端点在未配置 `API_KEYS` 时默认关闭；配置后每个 API Key 映射一个 `tenant_id`，查询强制带该租户条件。
- 配置 `API_SIGNING_SECRET` 后，时间戳、方法、路径和原始 query 必须使用 HMAC-SHA256 签名；生产建议同时使用 TLS、HMAC、Key 轮换、来源限制和速率限制。
- 当前端点是只读 GET：每日计划列表/详情、学期配置、班级配置；支持过滤、分页和资源不存在时的 404。API 不提供业务写入。
- API Key、API principal、tenant 规则不能与 UI JWT、UI session 或角色语义混用；“API 能按租户读取”不等于“UI 已成为多用户 SaaS”。

### 4.3 明确不支持或不应承诺的事项

当前不应在 PRD、销售材料或验收结论中承诺：

- Agent Provider 直接写数据库、改设置、创建/删除计划、写文件/Word/导出/备份、处理图片或调用远程对象。
- Agent 自动采用、批量或跨页面采用、“本次会话总是允许”、无人值守写入、失败后自动重试同一 WRITE、跨页面的待确认队列。
- Agent 的通用工具、动态 Tool 发现、shell/Python/SQL/MCP/插件访问、多 Agent、后台长期工作流或供应商托管长期记忆。
- Agent 在游戏观察、一对一倾听、自制教玩具或课程审议页面自动拥有同等能力；首期 Agent 只面向每日计划当前页。
- 对话、thread、embedding、summary、教师画像、完整 Patch 或 Provider 原文的长期持久化。
- 匿名注册、源码已知默认管理员密码或“启动即创建管理员”。
- `services/` 已经拆成可独立部署的 AI/Word/节假日微服务。
- 生产在线、用户规模、业务 KPI、所有 Windows/Word/MySQL/真实 AI/浏览器验收均已完成。单个健康接口、历史测试数字、Graphify 输出或单个平台结果都不能推出上述结论。

## 5. AI 能力与受控 Agent

### 5.1 既有单次 AI 生成能力

现有业务模块使用两类 AI：文本模型用于教案拆分、年龄适配、每日活动生成、自制教玩具和课程审议；视觉模型用于游戏观察和一对一倾听。共同产品原则是：

- AI 不是不可修改的事实，教师必须可以核对、修改和决定是否保存。
- AI 未配置、连接失败、返回结构错误或节假日服务不可用时，保留已输入内容并给出可理解的降级提示。
- 图片属于幼儿隐私，只有业务需要的数据才应发送给视觉模型；需求需明确数据处理、授权和保留策略。
- AI Key 在应用侧加密保存，界面只显示脱敏值；明文只应在当前调用的短生命周期内存在，不能进入日志、仓库或导出。

### 5.2 Foundation：四个 READ + 两个 DRAFT

受控 Agent 不是“开放式聊天机器人”，而是一条由应用控制的窄流程：

| 能力 | 产品含义 | 结果 |
|---|---|---|
| `daily_plan.read_current` | 读取当前已保存计划的白名单正文/摘要 | 只读投影 |
| `daily_plan.read_context` | 读取当前计划所需的班级、学期、周次、星期和栏目状态 | 只读投影 |
| `calendar.read_evaluation` | 判断指定日期的学期、工作日/节假日/未知状态 | 只读投影 |
| `settings.read_class_areas` | 读取当前 actor 可见的室内区域和户外内容 | 只读投影 |
| `daily_plan.draft_section_patch` | 针对登记栏目生成字段级建议 | 内存 `PlanPatch` |
| `daily_plan.draft_reflection_patch` | 针对一日反思生成字段级建议 | 内存 `PlanPatch` |

Agent 每轮从当前可信 `tenant/user` 和页面作用域重建最小 Context。Provider 只返回文本或请求上述关闭 Tool；Runtime 才执行 Tool，并负责 Schema、权限、调用次数、长度、超时、取消和过期结果校验。

### 5.3 当前可见的单 Patch 确认写入

当前工作树允许的 WRITE 是一个明确收窄的本地应用流程：

```text
Provider/Runtime 生成回答或 PlanPatch
        ↓（不写库）
当前页面展示目标、字段路径、before/after 和警告
        ↓
教师针对这一份 Patch 显式确认
        ↓
本地应用层重验会话、plan id、revision 和字段 before hash
        ↓
短事务：操作前完整版本 + CAS 更新 + 最小不可变审计
```

必须让 PM 记住以下边界：

- 确认是逐 Patch、逐次、当前页面的动作，不是为模型授予持续写权限。
- 只能作用于已经存在的当前每日计划和登记字段；不负责创建计划，也不按日期随便选第一条记录。
- `daily_plan.revision` 是并发控制权威版本；陈旧页面、错误会话、过期确认、before hash 不匹配或目标变化时应关闭本次采用。
- 已知失败全回滚；commit 结果未知时只允许用户显式发起只读对账，不能自动重放同一 Patch。
- Provider 和 Tool registry 仍没有 WRITE；设置、密钥、文件、Word、导出、图片、删除、创建和备份仍不因该能力获得 Agent 写权限。

详细的受控边界见 [`ADR-0005`](ADR/ADR-0005-controlled-ai-agent-runtime.md)、[`docs/design/agent-runtime.md`](design/agent-runtime.md)、[`ADR-0006`](ADR/ADR-0006-trusted-ui-session-and-confirmed-agent-write.md) 和 [`specs/agent-write/tests/README.md`](../specs/agent-write/tests/README.md)。

## 6. 数据、安全、审计与导出约束

### 数据与历史

- 默认使用 SQLite，服务器可使用 MySQL 8；所有 schema 变化必须通过 Alembic，当前工作树 head 为 `2b7f3d5e9c8a`。应用启动迁移失败时统一 fail-closed。
- 业务数据按 tenant/user 隔离；设置变化不会自动改写已保存记录，计划、观察、倾听等结果保留必要的年级/班级/教师快照。
- 游戏观察和倾听图片先做类型、大小、方向等约束，再以 BLOB 或后端对象标识保存；幼儿图片不得进入无关日志、测试 fixture 或仓库。
- 部分子表和导出记录使用逻辑关联而非完整数据库外键，删除、孤儿数据和跨 tenant/user 访问需要 service/repository 与测试共同守卫。
- `daily_plan.revision` 在成功内容更新时恰好递增一次；无变化、拒绝、回滚和失败不得递增。需求应明确并发冲突的用户提示和恢复动作。

### 密钥、会话与网络

- AI Key 以 Fernet 加密存储并脱敏显示；数据库密文必须与原加密密钥配对，`.kindergarten_secrets` 和运行数据目录需按平台收敛权限。
- 不在命令参数、聊天、`.env`、Git、日志、Issue、导出或截图中记录真实 API Key、数据库密码、JWT、HMAC secret 或完整数据库 URL。
- 登录、停用、降权、改密和重新登录会使不再有效的旧会话失效；UI callback 仍须做会话绑定检查。
- 对外暴露源码/Docker UI 时，TLS、网络白名单/防火墙、强密码和受控初始化是部署条件；桌面冻结版回环监听不等于所有部署模式安全。

### 日志与审计

- `log_audit` 是 AI、导出、关键设置和账号操作的安全日志边界；它不能替代 Agent WRITE 的事务内业务审计。
- Agent 确认成功时，操作前版本保存完整、精确的旧计划快照；`agent_write_audit` 只保存最小、不可变、可对账的信息。
- 审计不应包含 JWT/session 原文、密钥、endpoint、Prompt、Provider 正文、完整 Patch、原始异常或不必要的幼儿正文。
- Foundation READ/DRAFT、取消、过期、失败、丢弃和重启后的 Agent 状态不应写入业务表、预览、导出、备份或长期记忆。

### Word 与导出

- Word 导出使用仓库固定模板；模板字段映射、中文字体、图片方向/尺寸、差异标红、指标勾选和分页都是产品验收的一部分。
- 导出文件写入运行时 `exports` 目录并记录逻辑关联；备份策略应同时考虑数据库、密钥和必要导出。
- 自动结构测试不能替代 Microsoft Word/LibreOffice 的真实打开检查；不要把“生成了 DOCX”写成“版式已验收”。
- SQLite 运行中不能直接复制数据库作为唯一备份；正式流程应停机或使用一致性快照工具，并验证恢复。

## 7. 产品指标与验收建议（均为建议）

以下内容是为了帮助 PM 建立后续埋点和验收方案，**不表示当前已有这些埋点、目标值或历史 KPI**。采集时应避免保存幼儿正文、图片和密钥，优先记录脱敏的事件、耗时和结果码。

### 7.1 建议指标

| 指标方向 | 建议事件/定义 | PM 用途 |
|---|---|---|
| 业务完成 | 各模块“开始编辑 → 保存成功 → 导出成功”的漏斗；按模块、平台和数据库类型分组 | 找到流程中断点，不把 AI 成功率当作业务成功率 |
| 时间效率 | 从进入页面到保存/导出的耗时分布；拆分 AI 等待与人工编辑耗时 | 验证是否减少重复工作 |
| AI 稳定性 | 配置缺失、连接失败、解析失败、超时、降级和重试次数；不记录正文 | 区分配置问题、供应商问题和产品问题 |
| 人工控制 | AI 结果被修改后保存的比例、丢弃比例、重新生成比例 | 评估建议质量与教师控制感 |
| 并发安全 | stale/revision 冲突次数、成功更新次数、误写/回滚次数 | 验证多标签页和协作风险 |
| Agent 边界 | Agent 运行、取消、过期丢弃、Patch 生成、显式确认、应用成功、对账结果 | 证明受控能力被正确使用，不追求自动化写入量 |
| 导出质量 | 导出成功率、模板/字体/图片/分页缺陷反馈率、重新导出率 | 评估真正可交付的文档质量 |
| 集成安全 | API 401/HMAC 失败、租户拒绝、分页错误、健康检查与 readiness 分离状态 | 监控外部集成，而非把健康接口当业务指标 |

### 7.2 建议验收矩阵

每个需求至少写成“前置条件—用户动作—可见结果—持久化结果—失败恢复”的场景，并单独覆盖：

1. **主流程**：首次登录、基础配置、每个模块的手工完成、AI 可选完成、历史查看和导出。
2. **身份负向**：未登录、错误/过期会话、停用或改密后的旧标签页、角色限制、另一 tenant/user 的 ID 和子表访问。
3. **数据一致性**：全新 SQLite 迁移、MySQL 迁移、保存/覆盖/删除的事务边界、revision 冲突、图片和导出关联。
4. **AI 降级**：无 Key、Key 解密失败、网络失败、超时、错误结构、节假日未知；已有输入不得被失败结果覆盖。
5. **Agent 安全**：只出现 4 READ + 2 DRAFT；未知/WRITE Tool、额外参数、Prompt injection、跨作用域、取消、超时、迟到结果和重启均无越权或持久化副作用。
6. **确认写入**：只对当前页单 Patch 显式确认；校验 session、plan id、revision、before hash、过期与重复点击；已知失败全回滚，未知提交只读对账且不重放。
7. **文档质量**：使用目标版本固定模板在 Word/LibreOffice 中打开，核对中文、图片、差异、指标位置和分页。
8. **发布运维**：按安装方式分别验证数据目录、密钥权限、迁移、备份恢复、网络暴露、不可变镜像和回滚；使用固定 SHA/Tag 记录证据。

## 8. 路线图、风险与待决策

### 8.1 状态分层

- **已交付/已合入的工程边界**：Agent Foundation 的 4 READ + 2 DRAFT、零长期记忆，以及 Agent WRITE 所需的本地确认、revision、操作前版本和最小审计契约已进入当前代码/主线证据；Provider 仍无 WRITE。
- **当前受限能力**：Agent WRITE 仅限每日计划当前页面的一份 Patch、一次显式确认和本地应用层事务；只对已有记录生效。其他模块继续使用各自的常规 AI/手工/保存流程。
- **近期规划/待复验**：路线图 R2 优先完成一对一倾听完整 P8/P8d 人工验收，然后复验每日计划、游戏观察、自制教玩具、课程审议和只读 API；R5 下一步优先闭合 Issue #54 的数据库 readiness，再让 digest 部署/回滚使用 readiness 门禁，并继续备份恢复、目标平台、Word、MySQL 和真实 AI 验收。
- **产品深化方向**：R6 按“Word 模板中心 → 统一教学文档中心 → 教学审核与资源复用 → 幼儿成长档案和管理视图”逐步推进；详细范围、依赖、非目标和待决策项见 [`docs/PRODUCT_DIRECTION.md`](PRODUCT_DIRECTION.md)，规划跟踪见 [Issue #55](https://github.com/ywyz/kindergartenManager/issues/55)。该方向不构成实现授权。
- **产品建议**：在任何新 Agent Tool、批量采用、跨页面工作流、持久化待确认队列、家长端、多园 SaaS 或公网扩展之前，先冻结用户故事、数据保留/删除、授权粒度和人工恢复策略，再建立新的 ADR/spec/Issue 与稳定 RED。

### 8.2 主要风险

- **模块复验不足**：当前代码存在不等于当前 SHA 已完成 Windows、Word、MySQL、真实 AI 或浏览器人工验收。
- **事务边界不均匀**：一对一倾听和游戏观察的聚合写入已有更明确的 service/UoW 约束；其他历史写路径仍需逐项审计，不能由局部通过外推全仓库原子性。
- **页面复杂度**：部分 NiceGUI 页面同时承担展示、状态、数据库和业务编排，后续需求容易产生回归和权限遗漏。
- **逻辑外键与删除**：图片、子记录和导出关联多数由应用层维护，删除需求必须有孤儿清理和失败回滚场景。
- **部署健康误判**：`/api/v1/health` 是 liveness，不是数据库 readiness；部署验收需要独立的数据库就绪与恢复证据。
- **数据处理责任**：幼儿图片和文本是否可以发送到指定 AI、保留多久、谁可导出、如何删除，仍需园所制度和产品负责人明确，不能仅由技术实现推导。

### 8.3 需要产品负责人确认的问题

1. 首要目标用户是单园教师、教学管理者，还是多园/集团管理员？第一阶段是否只承诺单园本地或受控部署？
2. 三类角色的实际权限矩阵是什么：谁可查看、覆盖、删除、导出谁的数据？`teaching_admin` 是否跨教师查看？
3. 幼儿姓名、图片、观察文本和 Word 的保留、删除、导出审批、备份加密和 AI 外发规则是什么？
4. 文本/视觉模型的供应商、数据区域、失败降级和预算/延迟容忍度是什么？哪些场景必须完全离线可用？
5. Word 模板的验收人、Office 版本、中文字体、图片布局、分页和差异标红是否有签字标准？
6. 外部 API 的调用方、字段最小集、刷新/分页、HMAC/Key 轮换、来源限制和速率限制由谁负责？
7. Agent 单 Patch 确认是否满足真实教师故事？若未来需要批量、跨计划或创建计划，应如何定义授权、撤销、幂等和人工恢复？
8. 下一里程碑按“一对一倾听人工闭环”“发布运维”“事务/页面重构”还是外部集成优先？应为哪一个固定 SHA 和验收门负责？

## 9. PM 快速检查清单

在评审一个新需求或宣布一个模块可验收前，逐项回答：

- [ ] 用户、角色、tenant、user 和入口是否明确？UI 还是 `/api/v1`，是否误用了另一套身份？
- [ ] 目标模块的输入、可选 AI、人工编辑、保存、历史、删除、导出和失败恢复是否画成闭环？
- [ ] 幼儿数据、图片、Prompt、AI Key、Word 和日志的最小数据流、保留期与权限是否明确？
- [ ] AI 失败是否保留已有输入？模型输出是否始终可编辑，是否需要人工确认？
- [ ] 若涉及 Agent，是否仍只使用登记的 READ/DRAFT？是否明确 Provider 无 WRITE？
- [ ] 若涉及 Agent 采用，是否限定为当前页单 Patch，并绑定 session、plan id、revision、before hash、expiry 和一次性确认？
- [ ] 是否覆盖双击、多标签、切换日期、刷新、会话失效、stale、超时和 commit-unknown？
- [ ] 是否明确 SQLite/MySQL、迁移、备份恢复、图片大小/MIME、逻辑关联和事务要求？
- [ ] 是否使用真实固定模板完成 Word/Office 验收，而不是只检查文件存在？
- [ ] 指标是否标明为新增建议，避免把当前没有的埋点、用户规模或 KPI 写成既有事实？
- [ ] 是否为当前 SHA、目标平台、真实 AI/数据库和人工验收分别记录证据？是否误把 health、历史测试或图谱当成完整交付证明？
